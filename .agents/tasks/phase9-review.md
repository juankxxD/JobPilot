## Blocking findings

### P9-001 — The deployed workflow never provisions the required profile

The workflow checks out the repository and immediately installs, migrates, and runs (`.github/workflows/pipeline.yml:20-64`), but it has no step or secret for `profile.yaml`. That file is intentionally ignored (`.gitignore:3`) and is not tracked. The production command unconditionally loads `<project root>/profile.yaml` before constructing dependencies (`src/jobpilot/cli.py:136-139`, `src/jobpilot/cli.py:202-205`). Every scheduled or manually dispatched run therefore exits with “Profile not found” after migration instead of collecting or processing Telegram updates. Store the owner-approved profile in an appropriate GitHub secret or other protected deployment input, materialize it as `profile.yaml` with restrictive permissions before `jobpilot run`, and document that required deployment value without committing the profile.

### P9-002 — Missing optional Actions values override defaults with invalid empty strings

The workflow always exports `MAIL_PROVIDER`, `MIN_SCORE`, `DAILY_APPLICATION_LIMIT`, and `DEFAULT_LANGUAGE` from secrets/variables (`.github/workflows/pipeline.yml:45-57`). An undefined GitHub secret or variable expands to an empty string. `Settings` expects an enum or integer for those fields and only applies its defaults when the environment key is absent (`src/jobpilot/config.py:73`, `src/jobpilot/config.py:91-93`). A narrow construction check with the workflow's empty values failed validation for all four fields. This contradicts the deployment guide's statement that unset optional values use in-code defaults (`docs/deployment.md:32`, `docs/deployment.md:55-57`) and makes the documented minimal setup unable to start. Omit defaulted environment keys when unset or give the workflow explicit non-empty fallback expressions (and preferably use Actions variables for non-secrets such as model/provider/tenant); keep the documentation consistent with whichever values are truly required.

### P9-003 — Required native-PDF CI verification has no execution evidence

The recorded Phase 9 pytest run skipped all 9 WeasyPrint-dependent tests. The approved plan requires those tests to run in CI with the native libraries. Although the workflow installs the apt libraries, it installs only the base package (`.github/workflows/pipeline.yml:23-35`) and then runs only migrations and the production command (`.github/workflows/pipeline.yml:59-64`); no workflow in the repository invokes pytest, ruff, or mypy. The ATS tests explicitly rely on CI to disable their local native-library skip (`tests/conftest.py:49-95`, `tests/test_pdf_ats.py:1-69`). Consequently there is no required evidence that both language PDFs render and expose headers in ATS order under the deployment image. Add a CI verification job/workflow that installs the native libraries and dev dependencies and runs the required gate, then provide a successful recorded run in which the WeasyPrint tests execute rather than skip.

### P9-004 — Architecture and deployment docs overstate the accepted idempotency guarantees

The new architecture guide says every stage is idempotent, every Telegram update is processed exactly once, and any mid-run crash is harmless with no duplicate work (`docs/architecture.md:9-11`, `docs/architecture.md:58-61`, `docs/architecture.md:103-108`). The deployment guide similarly says schedule changes cannot affect correctness and that the offset makes long polling resume-safe (`docs/deployment.md:17-20`, `docs/deployment.md:63-80`). The approved ADRs explicitly record narrower behavior: an update may be checkpointed before a failed action and never resume, partial proposal delivery may duplicate attachments/uploads, the daily limit may be exceeded across runs, an ambiguous email transport failure may resend, and manual recording can duplicate after a partial DB failure (`docs/decisions.md:62-84`, `docs/decisions.md:105-116`). These claims can cause an operator to treat a crash or retry as safe when it can lose an owner action or duplicate externally visible work. Keep the approved deferred trade-offs, but scope the docs to normal/happy-path idempotency, disclose the known crash windows with links to ADR-011/012, and avoid promising exactly-once or resume-safe long polling until the outbox work exists.
