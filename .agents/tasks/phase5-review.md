## Blocking findings

1. **P5-012: The new cover-letter validator cannot detect invented technologies or facts.** `src/jobpilot/documents/cover.py:147-151` extracts technology names and then checks them against the profile, but `src/jobpilot/profile/validation.py:124-135` only extracts names already present in that same profile. Consequently `find_unknown_technologies` can never receive an unknown name from this path. No code validates the other factual claims in the free-form body. A narrow spot-check using `profile.example.yaml` confirmed that `_reject_reason("I led a Rust migration for 50 engineers.", ...)` returns `None` even though Rust and that claim are absent from the profile. This violates the profile-as-source-of-truth and code-validation rules in R1 and `design.md` (all cover technologies must be profile skills/tags; invalid output must retry/error), and can send a fabricated cover letter to the owner. Replace unrestricted prose acceptance with an enforceable constrained representation, such as approved profile fragment/achievement IDs plus code-rendered wording/tone, or otherwise validate every emitted claim and technology against cited approved profile facts. Retry once and mark the job `error` when validation still fails. Add a regression test with an unknown technology and an invented numeric claim.

2. **P5-013: Claiming an update before its effect permanently loses failed owner actions.** `process_telegram_updates` advances `telegram_last_update_id` before dispatch at `src/jobpilot/pipeline/run.py:607-614`. Language choice and free-text adjustment delivery failures are converted to `False` by `_try_proposal` (`src/jobpilot/pipeline/run.py:732-772, 544-547`) rather than completing the requested operation. The already-advanced offset then suppresses the update forever. A narrow spot-check made language proposal delivery raise `TelegramDeliveryError`: the first run reported one processed update but left the job `proposed` with no language, and replay processed zero updates because the checkpoint was already 7. The same mechanism clears the pending adjustment after a retryable failure at `src/jobpilot/pipeline/run.py:854-869`. The owner’s explicit Español/Inglés or Ajustar action can therefore disappear with no result and no retry, contrary to R10.4-R10.5, R14.2, and the design requirement that interrupted steps are resumable. Persist a per-update operation lifecycle rather than treating the fetch cursor as completion: durably record the intent, retry incomplete work, and mark/checkpoint it complete only after its required effects finish. Preserve enough document/delivery state to resume without repeating completed effects.

3. **P5-014: A partially delivered proposal is duplicated on retry.** `TelegramNotifier.send_message` sends each attachment separately and only then sends the button message (`src/jobpilot/channels/telegram.py:361-367`). `tailor_and_send_proposal` records `proposed` only after that whole sequence returns (`src/jobpilot/pipeline/run.py:376-381`). If the CV succeeds but the cover or final message returns `ok: false`, `_try_proposal` leaves the job `scored`; the next run regenerates and sends both attachments again. The same issue occurs when the first Drive upload succeeds and a later upload fails because no generated-file/delivery progress is persisted. This is a reachable duplicate-send/data path and violates R16.7 and the design statement that interruption must not duplicate work. Persist a proposal delivery record/outbox with generated file links and per-part completion (or use an equivalent resumable, idempotent delivery design), then resume only missing parts and transition to `proposed` after the complete proposal is confirmed. Add a regression test where the first attachment succeeds and the second send fails, followed by a rerun.

4. **P5-015: `DAILY_APPLICATION_LIMIT` resets for proposals on every pipeline run.** The guard uses only applications already recorded today plus `summary.proposed` from the current in-memory invocation (`src/jobpilot/pipeline/run.py:424-431`). It does not count proposals produced by earlier runs that day. Since prior proposals are no longer `scored`, a second scheduled run simply proposes the next batch. A narrow spot-check with ten distinct scored jobs and `daily_application_limit=5` produced five proposals on the first run and five more on the second, leaving ten proposals on the same day. This fails plan item 26 and its required test that the daily guard blocks extra proposals, and it makes the configured limit ineffective under the normal two-hour schedule. Persist an immutable proposal timestamp/event and include prior same-day proposals when calculating remaining capacity (without double-counting applications derived from those proposals), or enforce the limit through another durable daily reservation. Add a two-run same-day regression test.
